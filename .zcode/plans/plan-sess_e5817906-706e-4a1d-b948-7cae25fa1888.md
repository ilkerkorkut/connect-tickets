### Test 1: `TestBatchConcurrentRefreshSucceedsWithExactlyOnceGitHub`
Scenario: **5 repos, 5 jobs, 5 partitions, 5 concurrent workers, all succeed.**
Phases (each a numbered log step):
1. `setup dependencies_ready` — testkit environment.
2. `setup github_mock_ready` — httptest returning a distinct repo payload per `(owner,name)`; atomic call counter.
3. `seed batch_id=… repos=5 jobs=5 partitions=5`.
4. `kafka publish` per partition (logs `partition=… offset=…`).
5. `execution launch_workers=5 synchronization=shared_start_gate`.
6. `execution release_shared_start_gate` → each worker logs `partition=… claim_state=claimed attempt=1 outcome=succeeded`.
7. **Assertions** (logged as `phase=assertion …`):
   - All 5 `settlement.Commit==true`, no err.
   - GitHub mock `calls.Load()==5` (exactly-once per repo; no cross-repo coalescing since distinct keys). → `github_requests=5 exactly_once=true`.
   - All 5 jobs `status=succeeded`, `attempt_count=1`, no `last_error_code`.
   - Batch row `completed_at` set (auto-completion on last finish).
   - `repository_changes` count == 5; sequences are exactly `{1,2,3,4,5}` (sorted) — proves the `change_sequences` ForUpdate singleton serialized all writes with no gaps/dupes.
   - `repository_changes.event_id` all distinct; per-repo row count == 1.
   - Each repo's persisted row equals the mock payload (stars/owner/name/full_name).
8. Final summary log line: `phase=summary github_requests=5 succeeded=5 change_feed_sequences=1..5 batch_completed=true`.

### Test 2: `TestBatchRetryAndDLQWithExactlyOnceSemantics`
Scenario: **3 jobs, 3 partitions: (A) success, (B) rate-limited → retry-wait + outbox event, (C) repo-not-found → permanent failure + DLQ outbox event.**
Phases:
1. `setup` environment + **two** github mocks behind one httptest server: routes `/repos/<owner>/<nameB>` → 429 with `Retry-After: 20`, `X-RateLimit-Remaining: 0`; `/repos/<owner>/<nameC>` → 404; `/repos/<owner>/<nameA>` → 200. Atomic counters per outcome.
2. `seed` 3 repos + 3 pending jobs.
3. Publish to 3 partitions; process concurrently (shared gate).
4. **Assertions** (each logged):
   - A: `succeeded`, attempt 1, one `repository_changes` row.
   - B: `retry_wait`, attempt 1, `last_error_code=github_rate_limited`, `next_attempt_at != nil`, exactly **one** `outbox_events` row (`event_type=github.repo.refresh.v1`, `status=pending`, `aggregate_id=jobB`). GitHub called once for B.
   - C: `failed`, attempt 1, `last_error_code=github_repo_not_found`, exactly **one** `outbox_events` row (`event_type=github.repo.refresh.dlq.v1`, `status=pending`, `aggregate_id=jobC`). GitHub called once for C (the 404).
   - Exactly-once: GitHub counters per repo == 1; no duplicate outbox events; `event_id`s distinct.
   - `change_sequences`: only A advanced it (B and C do not insert change rows) → `repository_changes` count == 1, sequence == 1.
   - Batch not completed (B/C not terminal-succeeded but B is retry_wait and C is failed; `completeBatch` considers only `succeeded`/`failed` terminal → batch **completes** here; assert accordingly).
5. Summary: `phase=summary succeeded=1 retry_wait=1 failed=1 dlq_events=1 retry_events=1 change_feed_sequences=1`.

(Note: `completeBatch` marks batch done when no jobs remain in non-`succeeded`/`failed` status — `failed` is terminal, so with A=succeeded, B=retry_wait, C=failed the batch does **not** complete because B is still `retry_wait`. Test asserts `completed_at IS NULL`.)
