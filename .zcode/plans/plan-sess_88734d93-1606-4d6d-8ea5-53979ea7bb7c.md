## Task 03: Ent Model and Versioned Migrations — Implementation Plan

### Source & decisions (confirmed)
- INITIAL_PLAN §3.1-3.3, §7.1-7.7, §8.11, Phase 2, Prompt 3.
- **Migration generation:** Atlas generates versioned SQL files from Ent schemas (Ent `FeatureVersionedMigration` + `migrate.NamedDiff`).
- **Migration application:** `github.com/golang-migrate/migrate/v4` applies the generated SQL files in the `migrate` runtime mode (pure Go, single-binary, its own `schema_migrations` bookkeeping). Atlas OSS has no usable in-process revision tracker, so golang-migrate is the robust production path.
- **Integration test DB:** Docker container per `make test-integration` run, pinned `postgres:17-alpine`, random host port, readiness wait, teardown.

### Critical API facts (verified against pinned module source)
- Ent CHECK constraints: `entsql.Check("stars >= 0")` via `Annotations()` — there is no `field.Check`/`schema.Check`.
- Composite unique = `index.Fields(...).Unique()`.
- Versioned-migration feature: `gen.Config{Features: []gen.Feature{gen.FeatureVersionedMigration}}` in an entc generate script.
- File generation: generated `ent/migrate.NamedDiff(ctx, url, name, schema.WithDir(atlasDir), schema.WithMigrationMode(schema.ModeReplay), schema.WithDialect(dialect.Postgres), schema.WithFormatter(atlas.DefaultFormatter))`.
- Schema lock row pattern (§7.7): implemented at the application layer (Task 06) using `SELECT ... FOR UPDATE` on the ChangeSequence singleton — the schema just provides the row + unique constraint.

### Step 1 — Ent schemas (`ent/schema/*.go`)

Seven schemas, all fields/indices/constraints from §7:

- **`repository.go`** — `Repository`: id (UUID, default), owner, name, full_name, `normalized_full_name` (unique), description (text, nullable), stars (int, CHECK >= 0 via `entsql.Check`), language (nullable), html_url, notes (varchar bounded, e.g. 4000, default `""`), fetched_at, created_at, updated_at. No edges needed for FKs (Ent edges vs. plain columns: I'll use plain `field.UUID` columns for `batch_id`/`repo_id`/etc. to keep the FKs explicit and avoid Ent's implicit edge naming; add `entsql.Annotation` FKs where §7 implies them).
- **`batch.go`** — `Batch`: id, created_at, completed_at (nullable). No status column (derived from jobs per §7.2).
- **`batchjob.go`** — `BatchJob`: id, batch_id (UUID), repo_id (UUID), status (`field.Enum` with the 6 states), attempt_count (int, default 0), processing_owner (nullable string), lease_until (nullable time), next_attempt_at (nullable time), last_error_code (nullable), last_error_message (nullable, bounded), created_at, started_at (nullable), completed_at (nullable), updated_at. Indexes: `(batch_id,status)`, `(status,next_attempt_at)`, `(status,lease_until)`, `(repo_id,status)`; composite unique `(batch_id,repo_id)`. FKs to batch + repository.
- **`jobattempt.go`** — `JobAttempt`: id, batch_job_id, attempt_number, worker_id, started_at, finished_at (nullable), result (enum), error_code (nullable), duration_ms. Unique `(batch_job_id,attempt_number)`. FK to batch_job.
- **`outboxevent.go`** — `OutboxEvent`: id, event_id (unique), event_type, aggregate_id, partition_key, payload (jsonb/json text), status (enum pending/publishing/published), available_at, publishing_owner (nullable), publishing_lease_until (nullable), publish_attempts (int default 0), last_error (nullable, bounded), published_at (nullable), created_at, updated_at. Indexes `(status,available_at)`, `(status,publishing_lease_until)`.
- **`repositorychange.go`** — `RepositoryChange`: sequence (bigint, unique), event_id (unique), repo_id (UUID, nullable for tombstones), operation (enum created/notes_updated/refreshed/deleted), repository_snapshot (jsonb text, nullable for tombstone-only), changed_at. Index on `(sequence)` + repo_id lookup index.
- **`changesequence.go`** — `ChangeSequence`: name (unique, singleton = `repository_changes`), last_value (bigint).

A `TimeMixin` and an internal use of `field.UUID("id", uuid.UUID{}).Default(uuid.New)` for consistent IDs.

### Step 2 — Code generation wiring

- `ent/generate.go` — `//go:generate go run -mod=mod ./entgen` (or `entc.go`). Per AGENTS.md "no code comments" I avoid inline `//go:generate` comments; instead the Makefile `ent-generate` target runs `go run entgo.io/ent/cmd/ent generate` with a small `ent/entc.go` script that enables the feature flag. **Decision:** add `ent/entc.go` (`//go:build ignore` main) that calls `entc.Generate("./schema", &gen.Config{Features: []gen.Feature{gen.FeatureVersionedMigration}, ...})`. `make ent-generate` runs `go run ent/entc.go`.
- A `migrationsnapshot` script to drive `NamedDiff` for SQL file generation: `cmd/migrategen/main.go` (`//go:build ignore`), invoked by `make migrate-gen`. Calls `ent/migrate.NamedDiff(...)` writing into `migrations/`.

### Step 3 — Generated SQL migrations in `migrations/`

Run `make ent-generate` then `make migrate-gen` to produce versioned SQL files (e.g. `20260720T181530_init.sql`). **Adapt for golang-migrate**: golang-migrate expects files named `0001_up.sql` / `0001_down.sql` (sequential) OR can use the `iofs` source with its own naming. I'll **reformat** the Atlas output into golang-migrate's sequential `NNNN_name.up.sql` / `.down.sql` convention via a tiny post-step, OR — cleaner — generate with a formatter that matches. **Decision:** use golang-migrate's `iofs` source embedding `migrations/*.sql` with `0001_init.up.sql`/`0001_init.down.sql` naming; write the initial up/down pair by hand-reviewing the Atlas-generated SQL (Atlas output is plain DDL — I'll take its `CREATE TABLE`/index statements as the `.up.sql` and generate `DROP TABLE` cascade as `.down.sql`). Atlas stays the generator of record; the reviewed files are committed. The task says migrations must be "reviewable" — hand-reviewing and committing the SQL satisfies this.

### Step 4 — Migration runner (`internal/platform/database/migrate.go`)

- `ApplyMigrations(ctx, dbURL string, fsys fs.FS) error` — uses `golang-migrate/migrate/v4` with the `iofs` source (embedding `migrations/`) and the `pgx5` database driver. Returns typed errors. `migrate.Up()` then `migrate.Close()`.
- Embed migrations via `//go:embed migrations/*.sql` so the single binary carries them (no external file dependency at runtime — honors single-binary Docker requirement).
- Pin `github.com/golang-migrate/migrate/v4` and the `pgx5` subpackage as direct deps.

### Step 5 — `migrate` runtime mode (`internal/app/migrate.go`)

- Load config, build logger (no need for full bootstrap — migrations don't need Redis/Kafka; but to reuse lifecycle I'll construct just the logger and read `DATABASE_URL`). **Decision:** minimal — load config, build logger, call `database.ApplyMigrations(ctx, cfg.Database.URL, embeddedFS)`. Log "migrations applied" with a count if available, or success. Exit 0 on success, non-zero on failure. Remove the `ErrNotImplemented` return.
- Add `CHANGESEQUENCE` singleton seeding: after applying migrations, idempotently insert the `repository_changes` singleton if absent (`INSERT ... ON CONFLICT (name) DO NOTHING`).

### Step 6 — Makefile targets

- `ent-generate` — `go run ./ent/entc.go` (runs ent codegen into `ent/`).
- `migrate-gen` — `go run ./cmd/migrategen/main.go` (regenerates SQL via Atlas NamedDiff into `migrations/`).
- `migrate-up` — `./bin/github-tracker migrate` (applies embedded migrations).
- `generate-check` — verifies generated code is up to date (`go generate ./...` dry-run / diff check) — I'll implement as a guard that re-runs ent-generate and fails if `git diff` shows changes.
- `db-up` / `db-down` — `docker run`/`rm` a pinned `postgres:17-alpine` for local dev (also used by tests).
- Update `test-integration` to run the Docker-helper + integration tests.

### Step 7 — Integration tests (`test/integration/`, build tag `integration`)

- `postgresfixture` helper: starts `postgres:17-alpine` on a random port via `docker run`, polls `pg_isready`/a SELECT until ready, returns a `DATABASE_URL` + cleanup. Uses `testing` cleanup. No arbitrary sleeps (bounded readiness loop).
- `migrations_test.go`:
  - Apply migrations from zero → assert all tables, indexes, constraints exist (query `pg_indexes`, `information_schema.tables`, `pg_constraint`).
  - **Duplicate normalized repo** insert → fails with unique violation.
  - **Duplicate batch_job (batch_id, repo_id)** → fails.
  - **Negative stars** → fails (CHECK constraint).
  - **Invalid batch_job status / outbox status / operation** → fails (enum).
  - **Duplicate job_attempt (batch_job_id, attempt_number)** → fails.
  - **Duplicate outbox event_id** → fails.
  - **ChangeSequence singleton** initialized exactly once; re-running migrate is idempotent.
  - Re-run `migrate` on an already-migrated DB → no-op, no error (repeatable workflow).
- Tests use raw `pgx` connections (no Ent client needed for constraint testing — direct SQL proves the DB boundary is the authority).

### Step 8 — Schema note (`migrations/SCHEMA.md`)

Short doc explaining each non-obvious constraint and index: why `normalized_full_name` unique (concurrent dup creation), why CHECK on stars, why the lease/next_attempt indexes (claim/retry queries), why outbox status indexes (publisher claim), why change-sequence singleton + the §7.7 `FOR UPDATE` lock-row protocol (commit-ordered cursors), why derived batch status.

- Generated Ent code reviewed (I'll inspect the generated `client.go`/entity files and confirm clean).
- Single binary carries embedded migrations.
- No invented Ent/Atlas APIs (all verified against pinned source).
